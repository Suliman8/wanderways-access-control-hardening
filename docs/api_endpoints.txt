5. FIRST OBSERVATIONS - leads for Task 2 (not exploited yet)
----------------------------------------------------------------------------------------------
 1. /api/v1/bookings and /api/v1/bookings/{id} answer 200 with NO login and return every
    booking, including passport numbers and card digits.
 2. /api/internal/debug answers 200 with NO login. The response contains a "secret_key" field
    (the Flask session signing key).
 3. /api/admin/users answers 200 to the customer and the agent. /api/admin/stats correctly
    answers 403 to them, so the admin role check is applied to some routes but not others.
 4. /admin (admin panel page) loads for the customer and the agent. Only the menu link is
    hidden from them.
 5. IDs are sequential. sara.agent got 200 for /api/bookings/1, which is assigned to
    bilal.agent, and the customer got 200 for /api/users/1, the admin's account. Likely IDOR.
 6. The server allows DELETE on /api/bookings/{id}, but the UI has no delete button. Who is
    allowed to delete must be tested.
 7. /api/admin/bookings/export answers 403 (not 401) even without a session. Login also sets
    a readable, unsigned cookie "ww_role=<role>" next to the session cookie. The export
    route may be trusting that cookie.
 8. The UI only sends dates, travellers and notes in PUT /api/bookings/{id}, and only
    name, email and phone in PATCH /api/users/{id}. Whether extra fields (status,
    total_price, customer_id, role) are also accepted must be tested.
